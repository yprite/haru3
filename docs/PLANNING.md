# IamInJapan - 일본어 학습 앱 종합 기획서

## 1. 앱 개요

### 1.1 비전
**"어른도 부담 없이, 10분씩 짧게 학습해도 일본어가 오래 기억되는 학습 앱"**

### 1.2 핵심 가치
- 뇌과학 기반 학습 설계로 장기 기억 형성
- 일상 대화 가능한 600~800개 문장 마스터
- 하루 10분, 3문장씩 부담 없는 학습량
- 실제 상황(카페, 지하철, 쇼핑 등) 기반 맥락 학습

### 1.3 타겟 사용자
- 일본 여행을 준비하는 성인
- 바쁜 일상 속 틈새 시간에 학습하고 싶은 직장인
- 기존 암기식 학습에 지친 학습자

## 2. 뇌과학 기반 학습 설계 원칙

### 2.1 핵심 원칙 7가지

| 원칙 | 설명 | 앱 적용 방식 |
|------|------|-------------|
| **Spacing Effect** | 간격을 두고 반복할수록 기억 유지 | 0/3/7/14/30일 SRS 자동 스케줄링 |
| **Retrieval Practice** | 회상 시도가 기억 강화 | 일본어 가리기 → 떠올리기 → 말하기 |
| **Chunking** | 정보를 덩어리로 묶으면 기억 용이 | 문장을 2~4개 청크로 분해 설명 |
| **Interleaving** | 다양한 패턴 교차 학습 | 하루 3문장, 서로 다른 패턴 |
| **Context Learning** | 맥락 속 학습이 전이 효과 높음 | 카페/지하철/쇼핑 등 실제 상황 |
| **Multi-sensory** | 다중 감각 활용이 기억 강화 | 듣기→보기→말하기→조립 |
| **Peak-End Rule** | 마지막 경험이 전체 인상 결정 | 세션 종료 시 성취감 강화 피드백 |

### 2.2 SRS (Spaced Repetition System) 설계

```
학습 완료 → 3일 후 복습 → 7일 후 → 14일 후 → 30일 후
    ↓           ↓           ↓          ↓           ↓
  Day 0      Day 3       Day 10     Day 24      Day 54
```

복습 시 틀리면 → 간격 리셋 (Day 0부터 재시작)

### 3.1 Level 구성 (총 600~800문장)

### 7.4 데이터 저장소 확장 전략

#### JSON의 한계점

| 한계 | 설명 | 영향 시점 |
|------|------|----------|
| **스키마 버전 관리** | 필드 추가/삭제 시 마이그레이션 어려움 | 콘텐츠 구조 변경 시 |
| **관계형 데이터** | 문장↔카테고리↔레벨 관계가 중복/비효율적 | 2,000문장+ |
| **부분 업데이트** | 문장 1개 수정해도 전체 파일 교체 필요 | 잦은 콘텐츠 업데이트 시 |
| **복잡한 쿼리** | "Level 1의 미완료 문장만" 같은 필터링을 코드로 직접 구현 | 고급 기능 추가 시 |
| **다기기 동기화** | 로컬 저장 한계로 여러 기기 간 진도 동기화 불가 | 사용자 요청 증가 시 |

#### MVP에서 JSON이 적합한 이유

```
┌─────────────────────────────────────────────────────────────────┐
│  600~800문장 ≈ 300~500KB JSON                                   │
│                                                                 │
│  ✓ 메모리에 전부 올려도 모바일에서 문제없음                        │
│  ✓ 복잡한 쿼리 불필요 (전체 로드 후 Array.filter로 충분)          │
│  ✓ 오프라인 완전 지원 (네트워크 의존성 제로)                       │
│  ✓ 개발 속도 최대화 (DB 설계/마이그레이션 불필요)                  │
│  ✓ 배포 단순화 (앱 번들에 포함)                                   │
└─────────────────────────────────────────────────────────────────┘
```

#### Repository Pattern이 확장을 가능하게 하는 이유

```typescript
// 인터페이스 (변경 없음)
interface ContentRepository {
  getSentencesByCategory(id: string): Promise<Sentence[]>;
  getDailySentences(date: string): Promise<Sentence[]>;
}

// Phase 1: JSON 구현체
class LocalJSONRepository implements ContentRepository {
  getSentencesByCategory(id: string) {
    return Promise.resolve(
      SENTENCES.filter(s => s.categoryId === id)
    );
  }
}

// Phase 2: SQLite 구현체
class SQLiteRepository implements ContentRepository {
  getSentencesByCategory(id: string) {
    return db.query(
      'SELECT * FROM sentences WHERE category_id = ?', [id]
    );
  }
}

// Phase 3: API 구현체
class RemoteAPIRepository implements ContentRepository {
  getSentencesByCategory(id: string) {
    return fetch(`/api/sentences?category=${id}`).then(r => r.json());
  }
}
```

**핵심:** UI와 비즈니스 로직은 `ContentRepository` 인터페이스만 의존하므로,
데이터 소스가 JSON → SQLite → API로 바뀌어도 **코드 변경 최소화**.

#### 전환 결정 체크리스트

| 신호 | 현재 상태 확인 | 전환 고려 |
|------|--------------|----------|
| 콘텐츠 1,500문장 초과 | JSON 파일 1MB+ | SQLite 전환 |
| 사용자 1,000명 초과 | 다기기 동기화 요청 | 서버 DB 도입 |
| 콘텐츠 업데이트 주 2회 이상 | 앱 재배포 부담 | 서버 콘텐츠 분리 |
| 개인화 추천 필요 | 학습 패턴 분석 요구 | 서버 분석 파이프라인 |
| 소셜/경쟁 기능 추가 | 랭킹, 친구 기능 | 실시간 서버 필수 |
